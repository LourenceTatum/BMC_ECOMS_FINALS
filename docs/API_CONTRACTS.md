# API Contracts

Wire contracts between the Flutter app and the backend. These are **specifications
for Phase 5/6 implementation**, not existing endpoints. Field names use
`camelCase` on the client boundary; DB columns use `snake_case`.

## 0. Conventions

- Function invocation: `supabase.functions.invoke('create-checkout-session')`
  with the user's JWT automatically attached; server must still verify it.
- Successful JSON responses use 2xx; errors use an `{ "error": { "code",
  "message" } }` envelope with stable codes (see `ERROR_HANDLING.md`).
- Idempotency keys are UUID v4 generated by the client per checkout intent.

## 1. create-checkout-session (Edge Function)

### Purpose
Authenticated Buy Now (and cart checkout) → create pending order + payment
attempt + inventory reservation, create Xendit hosted session, return handoff
data. Never trusts client pricing.

### Auth requirement
- **Required**: valid Supabase user JWT. 401 if absent/invalid.

### Request
```
{
  "mode": "buy_now" | "cart",
  "idempotencyKey": "uuid-v4",
  "lineItems": [ { "productVariantId": "uuid", "quantity": 2 } ],   // mode=buy_now: 1 entry
  "shippingAddressId": "uuid"
}
```
- `mode=buy_now` requires exactly one line item.
- Client quantities and variant ids are **hints**; the server re-reads the
  catalog and clamps/rejects.

### Server behavior (summary; see PAYMENT_ARCHITECTURE.md Stages 3–5)
1. Verify JWT; load user profile.
2. In a transaction: lock variants, validate active product/variant, compute
   price from DB, check stock (incl. active reservations), insert orders +
   order_items (snapshots) + reservation; enforce `idempotency_key` uniqueness.
3. Call Xendit Sessions (server secret); persist `payments` row.
4. If the same key already exists for this user, return the stored result.

### Success response `200`
```
{
  "orderId": "uuid",
  "orderNumber": "BMC-XXXXXX",
  "checkoutUrl": "https://checkout.xendit.co/web/....",
  "expiresAt": "2026-11-01T10:00:00Z",
  "paymentStatus": "pending",
  "amount": "1599.00"            // string decimal (PHP), informational
}
```

### Error responses
```
400 { "error": { "code": "validation_failed", "message": "..." } }
401 { "error": { "code": "unauthenticated", "message": "Sign in to continue." } }
404 { "error": { "code": "product_unavailable", "message": "..." } }
409 { "error": { "code": "variant_out_of_stock", "message": "..." } }
409 { "error": { "code": "conflict", "message": "idempotency key belongs to another user" } }
502 { "error": { "code": "checkout_provider_error", "message": "Payment host unavailable, retry" } }
```
- Client behavior: map codes to UI messages; retry 502 once with the same key;
  never create a new key silently.

### Database effects
- Inserts: `orders` (1), `order_items` (1..n), `inventory_reservations` (1..n),
  `payments` (1). No client-visible grants needed to perform these.

## 2. xendit-webhook (Edge Function)

### Purpose
Trusted intake for Xendit events. Verifies authenticity, dedupes, enforces
transitions (`PAYMENT_ARCHITECTURE.md` Stage 7).

### Auth requirement
- **None at the JWT level** (providers cannot hold user sessions).
- **Mandatory**: `X-Webhook-Token`/`x-callback-token` header must match
  `XENDIT_WEBHOOK_VERIFICATION_TOKEN` (constant-time compare). Mismatch → 401.
  (Exact header name from official docs is confirmed in Phase 6; the token value
  is a server secret.)

### Request (provider event — shape confirmed in Phase 6)
```
{
  "event": "payment.capture" | "payment.failure" | "payment_session.completed"
            | "payment_session.expired" | ...,
  "data": { "id": "<session-or-payment id>", "reference_id": "...",
            "payment_id": "...", "capture_id": "...",
            "amount": 159900, "currency": "PHP", "status": "CAPTURED", ... },
  "created": "...", "id": "<event id>"
}
```

### Server behavior
1. Return 2xx immediately; process the rest asynchronously.
2. Verify token; parse event; locate `payments` by `provider_session_id` or the
   reference in `data.reference_id`.
3. Dedupe on the provider event id (`payments.provider_event_id` unique); no-op
   if already applied.
4. Validate amount/currency/reference against the stored `payments` row.
5. Apply transitions in one transaction with conditional updates (capture →
   `succeeded`/`paid` + fulfill reservation + decrement stock; failure →
   `failed` + release; expired/cancel → respective + release).

### Response
- `200 {"received": true}` for all successfully received (incl. duplicates and
  mismatches logged-but-ignored) — prevents provider retry storms.
- `401` for token mismatch (genuine unauthorized attempts).

### Database effects
- Updates `payments` (+ 1 insert of event trace into `raw_payload` history),
  `orders` (payment_status/status/paid_at), `inventory_reservations`,
  `product_variants` (stock decrement).

## 3. Order/payment status retrieval (client)

Owners read their status directly via RLS-authorized PostgREST — no separate
function in MVP:

```
GET /rest/v1/orders?select=id,order_number,status,payment_status,total,currency,
  created_at,paid_at,order_items(*),payments(provider,status,amount,paid_at)
  &id=eq.<orderId>
```

- `GRANT SELECT` + RLS restrict to `user_id = auth.uid()`.
- **Forbidden**: requesting another user's order returns empty/404 — the client
  maps that to the not-authorized state (`AUTHENTICATION.md` §8).
- Order detail rendering uses `order_items` snapshots (never live product
  prices) + the payments row for status chips.

## 4. Table of auth + expectations

| Operation | Transport | Auth | Idempotent | Server privileged |
|---|---|---|---|---|
| create-checkout-session | functions.invoke (POST) | user JWT | yes (key) | yes |
| xendit-webhook | HTTP POST (public path) | callback token | yes (event id) | yes |
| status fetch | PostgREST SELECT | user JWT + RLS | read-only | no |
| cart writes | PostgREST | user JWT + RLS | n/a | no |
| profile/address writes | PostgREST | user JWT + RLS | n/a | no |
